## Debate evidence

- `DeskScreen.orbPlanCard` shows a persisted V3 ORB plan as “research plan only” and has no position-report action. `LightningDeskModel.publishORBDecision` writes the plan and lifecycle event to the Live OANDA research archive.
- `LightningDeskModel.lockInTrade` is a separate legacy binary-style flow: it accepts a `ScanCommit`/`EngineSignal`, creates `ActiveTrade`, and stores `ActivePositionRecord`. It has no V3 `planID`; it must not produce V3 spot-position evidence.
- `V3PlanEntryEvidence` stores a full `V3MarketObservation` (bid/ask, source time, receipt time), quality, and exact `planID`. It represents an observed market entry reference, not a user’s fill report. The current ForwardTest and authentic replay producers mark it `.simulated`.
- `V3PositionRecord` already represents `.userReported` with `.manualTradeReport`, exact optional `planID`, instrument, side, units, and optional entry price. It has only `updatedAt`, so actual user-reported entry time is not distinguished from record time. Validation checks fields but there is no archive-wide supersession/correction chain validator.
- `ResearchStore` writes immutable position records under `v3-position-events`; same-ID changed content conflicts. It does not cross-check the record’s plan, instrument, and side against an exact plan in that archive. Review joins by exact `planID`, flags instrument conflicts, but its position timeline omits `entryPrice`.
- Three read-only audits independently agreed that a plan-scoped `.userReported` position is a suitable next scope if it remains explicitly user-authored, unverified evidence. They rejected reusing legacy `lockInTrade` or synthesizing a `V3MarketObservation` from a user-entered fill price.

## Ranked scope proposal

1. Add a separate explicit user-report flow available from a V3 plan, never from the binary `Lock In` control. The user must confirm they already opened the spot position outside BlazerOS. The flow records evidence and performs no order action.
2. Support only the Live OANDA archive for the first production writer. Require an exact plan identity from that archive and validate plan existence, instrument, side, and root together. Current plans may be reported from Trade; historical reports may be started from exact Live OANDA plan detail in Review. Never infer a replacement plan when the selected plan is stale, invalidated, or expired.
3. Record only `state = .userReported` and `provenance = .manualTradeReport`. Keep broker name/position ID absent. Display the result as an unverified user-reported position, never as broker open or filled state. The plan's reference units and the user's actual units must have distinct labels.
4. Add optional user-entered actual entry price and entry timestamp as distinct fields from `updatedAt` (report time). When supplied, require finite positive price and `plan.createdAt <= userReportedEnteredAt <= updatedAt + 5 seconds`. `updatedAt` is generated from the device clock at submission; a value more than five seconds in the future is rejected. Older records without the new optional fields must remain decodable. Do not fabricate a V3 bid/ask observation; retain `V3PlanEntryEvidence` for genuine market observations only.
5. One aggregate user-reported position is allowed per plan in this first writer; the entered units represent the user's total position size and are labeled separately from plan reference units. Derive a stable logical `positionID` from the exact plan ID. Enforce at most one root record for that positionID; the serialized first write wins and a concurrent/double initial submission with different substantive payload conflicts. If legacy same-plan `.userReported`/`.manualTradeReport` rows lack `positionID`, block creation of a new aggregate for that plan and surface “existing report requires review”; do not create a parallel root. Derive each record ID from positionID, predecessor ID, and canonical substantive payload; exclude only device-generated `updatedAt` from this digest. Exact retry therefore finds the same record ID and preserves the first stored timestamp; substantive changes require an explicit correction. Corrections append a new record with `supersedesRecordID`. Accept a correction only when it points to the sole unsuperseded predecessor for the same positionID, exact plan/root, instrument, side, `.userReported` state, and `.manualTradeReport` provenance. Reject branching, cycles, cross-plan/root links, and supersession of broker records. Older rows without position IDs remain standalone records and block new creation for their plan.
6. Keep persistence status independent of the ORB plan/lifecycle projection. On write/read failure, preserve the displayed research plan, expose a bounded unavailable message, and do not claim the report was recorded.
7. Show entry price/time, user-report quality, and supersession links in the exact-plan Review timeline; retain source-specific unavailable and orphan behavior.

## Design contract for challenge

- Entry point is a dedicated V3 plan action such as “Record position I opened”; it is distinct from “Lock In” and any broker/order ticket. The confirmation copy states that the user already opened the position outside the app. Historical entry is available from exact-plan Review detail, with explicit historical/stale/terminal labeling.
- User reports are not independently verified fills. Persist no broker IDs, no `.brokerOpen` state, and no `BROKER_EXECUTION` provenance. Do not automatically transition ORB lifecycle or mutate the plan state based on this report.
- Persist only against the exact immutable plan ID in `live-oanda`. If the plan cannot be reloaded and validated, fail closed. Invalidated/expired plans may accept a report as historical fact only; terminal lifecycle state stays terminal and can never be reopened by the report. If actual `userReportedEnteredAt` is after the plan's terminal lifecycle source time, allow the user report but label it “outside plan window”; if entry time is missing, label timing unavailable and do not imply it preceded the terminal event.
- Separate actual reported `userReportedEnteredAt` from report `updatedAt`; missing optional actual details remain explicitly unavailable. No current quote may be represented as the historical fill or as a fabricated bid/ask pair.
- Records are append-only. Stable plan-derived `positionID` identifies the plan's one aggregate user-reported position; at most one root is permitted. Stable payload-derived record ID identifies each retryable revision. Exact replay ignores only the device-generated `updatedAt` and retains the first value. Corrections form one non-branching chain of same-plan user reports; the leaf is current and ancestors remain visibly superseded. Corrupt, duplicate-root, cyclic, cross-plan, cross-root, or broker-record supersession links make the source unavailable or the chain unresolved. A legacy same-plan manual-report row without positionID blocks a second root until explicitly resolved.
- Read-plan, validate-chain, and append are one serialized operation per normalized archive root across ResearchStore instances. Existing records without optional new fields retain their current decoding and display behavior. Failed writes leave the plan and lifecycle evidence unchanged.
- Manual report handling never creates broker orders, changes account credentials, or affects the legacy binary trade path.
- Positive UI acceptance uses only a `DEBUG` + iOS Simulator fixture activated by explicit `--ui-testing-user-report` launch argument. The branch must be the first action in `LightningDeskModel.run()`, short-circuiting before credential loading, engine boot, assistant startup, candle fetch, network, or scan. It seeds one deterministic validated plan through the app-process ResearchStore into the simulator app's sandboxed `live-oanda` research root, with exact-replay identity, and exposes the ORB report form. It must not access credentials, start network/broker work, or compile into Release/device builds. The UI test opens the form and checks confirmation/no-order/unverified accessibility copy, then verifies no position report was persisted; it never taps submit. Persistence is covered separately by ResearchStore tests.
