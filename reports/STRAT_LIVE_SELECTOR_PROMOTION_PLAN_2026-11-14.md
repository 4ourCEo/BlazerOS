# Live Strategy Selector Promotion Gate — 2026-11-14

## Debate findings

- Independent selector audit found that `LiveStrategySelector` accepts fresh candidates without consulting `StrategyResearchRegistry`. Thus ORB, Candidate001, and Candidate002 profiles marked `RESEARCH_CANDIDATE` can currently contribute to a production Live BUY/SELL.
- The same audit found several registered strategies are not evaluated by `LightningDeskModel.selectLiveStrategyDecision`; registry presence is not evidence that the Live engine uses a family.
- Independent design challenge agreed that research maturity, Live signal eligibility, and order authority must be separate. It found the initial proposal incomplete because it omitted legacy persisted decisions, aggregation of multiple Legacy policy variants, and the fact that strict gating means no Live BUY/SELL until a profile is promoted.
- User intent requires explicit strategy-derived signals with a visible explanation. The source-backed candidates must remain inspectable in a separate research view, but must not be described as production signals or trigger actionable notices until eligible.
- Existing order safeguards remain: profile promotion never grants broker-order authority; `mayAuthorizeOrder` stays false.
- Independent implementation reviews found two additional selector input gaps before integration: active plan state was not checked (`V3TradePlan.validation()` accepts DRAFT/INVALIDATED/EXPIRED), and `spreadState == .accepted` was trusted without validating numeric spread. Both require explicit guards and fixtures.
- A second independent review found campaign/profile configuration digest was not bound to the candidate actually evaluated. Candidate contracts and adapters must carry a canonical evaluated-configuration SHA-256, and selector promotion requires equality with both profile and promotion record. Missing/mismatched configuration provenance stays shadow.
- Registry exact candidate identities must be unique; ambiguous duplicate mappings fail closed and have regression coverage.

## Revised design challenge

The first independent challenge returned PARTIAL. The following specifics are now part of the design for re-review:

- **Restore path:** `LightningDeskModel.restoreLiveStrategyDecisions()` already restores prior actionable decisions as WAIT with no plan, retaining the stored event as history. Preserve this behavior and add tests for actionable-with-plan, actionable-without-plan, unknown profile/version, and post-demotion cases; no restored historical signal may create a notification or current plan projection.
- **Restore freshness:** Every persisted actionable decision restores as WAIT with no current plan, regardless of promotion status. Only a fresh Live OANDA evaluation may publish a new BUY/SELL. Tests must prove no restored event creates a signal notification.
- **Decision provenance:** Add selected profile ID/version/instrument, promotion record ID, configuration/evaluator/adapter digests, supporting profile IDs/versions, and selector-policy version+implementation digest to `LiveStrategyDecision`. New provenance fields decode optionally for old stored records; a legacy record without exact provenance cannot reappear as actionable.
- **Legacy aggregation:** All four existing `ScanPolicy` variants (`baseline`, `continuation`, `reversal`, `regime`) are included in one control observation. All four must be fresh, eligible, directional, and unanimous before Legacy can veto a promoted strategy. Any stale/missing/invalid or disagreeing variant makes the control neutral. Legacy never supplies a plan or quorum vote.
- **No current promotion:** All current profiles remain `shadow`; Live Trade displays WAIT with the reason that no strategy profile has passed the Live promotion gate. A separate “Research evaluations · non-actionable” area may show strategy name/version, evaluated/rejected state, and precise rule reason only. It must not show direction, entry/stop/target levels, use BUY/SELL signal-banner styling, show a CTA, project a plan, or create a signal notification. The list is populated only from the current Live OANDA evaluation and is not restored across launch.
- **Exact identity:** Registry entries declare exact accepted strategy IDs and evaluator versions (including intentional aliases). Unknown IDs and version mismatches are ineligible, and never fall through to Legacy.
- **Promotion proof:** Add an explicit promotion record bound to exact profile ID/version/instrument, preregistered hypothesis ID, effective configuration digest, evaluator source digest, adapter source digest, selector-policy and selector-code digests, campaign manifest digest, held-out artifact digest, and a separate owner-approval record. A qualifying campaign must use chronological data, declared spread/commission/slippage assumptions, a protected held-out set, and validation criteria preregistered before looking at that set; promotion requires the held-out result to pass those criteria. A completed campaign that fails is not promotion evidence. Synthetic/incomplete campaigns cannot qualify. Store immutable campaign artifacts under `reports/research-campaigns/<campaign-id>/` and approval/promotion records under `reports/strategy-promotions/<profile-id>/<version>/`.
- **Runtime trust:** The installed app must not read repository-relative reports. Packaging generates and embeds a build-input manifest plus compact promotion/approval/evidence summaries under `Contents/Resources/StrategyPromotions/`; original datasets and full campaign artifacts remain archived in the repository. The manifest records exact per-profile dependency-closure source digests and all declared Swift package/toolchain/build/generated inputs. The trusted staged packager hashes each declared input closure before and after a fresh isolated release build and fails if they differ. It does not place an executable digest in the embedded manifest or claim a runtime source-to-binary reproducibility check. The owner-pinned non-ad-hoc app code signature (exact certificate fingerprint or Team ID) seals the executable and manifest as one bundle. At runtime the app verifies the fixed bundle ID, complete code signature and pinned signer, signed manifest/promotion/campaign/approval digests, profile/config/policy, and campaign PASS before supplying promotion records. Missing, malformed, stale, mismatched, invalidly signed, or unverifiable records fail closed to shadow. Production registry has no promotion records today. Promotion and `mayAuthorizeOrder` remain independent; `mayAuthorizeOrder` stays false.
- **Plan selection:** An explicitly promoted strategy may signal under its own validated contract. Cross-strategy agreement is required only when its exact, versioned selector policy says so. The default policy permits one unique eligible structural plan; zero plans, two or more distinct plans, opposing promoted candidates, or incompatible side/levels produce WAIT. Identical plans deduplicate only when their complete validated plan identity is equal. Ordinal `rankingScore` never chooses between plans.
- **Plan and quote gates:** Only a `.validated` plan can create a production signal. DRAFT, OFFERED, TRIGGERED, INVALIDATED, and EXPIRED states are rejected. Candidate spread must be present, finite, and positive; structural candidates must also have spread at or below their plan's `maxSpread` even when the upstream enum says accepted.
- **Evaluated configuration binding:** Add optional configuration and code-digest provenance to candidates with backward decoding. Hash a domain-separated `BLAZEROS_EFFECTIVE_CONFIG_V1` envelope containing profile ID/version, evaluator version, adapter version, instrument, the exact Codable configuration instance passed to the evaluator, and every behavior-affecting adapter setting (aggregation, plan construction, pip scale, session/calendar). Use one versioned sorted-key JSON encoder with fixed millisecond date encoding and lowercase SHA-256; reject non-finite values and encoding failures instead of hashing a sentinel. Golden vectors pin the encoding. Profile config digests are keyed by instrument. Live selection requires exact equality across candidate, instrument-specific profile, and promotion records; nil or unknown provenance is ineligible. Legacy control is not a promoted profile and is unaffected.
- **Evaluator code identity:** Each candidate and promotion binds exact evaluator, adapter, and selector implementation source digests in addition to versions. The build-input manifest declares the complete source dependency closure for each family: evaluator, adapter, candidate/config contracts, `LiveStrategyDecision.swift`, `StrategyResearchRegistry.swift`, `V3DomainContracts.swift` plan validation, and every shared aggregation, pip, session/calendar, and plan-construction helper used by that evaluator. It also binds `Package.swift`, `Package.resolved` when present, Swift toolchain, build flags/configuration, generated/macro-produced inputs and their generators. Tests and release packaging recompute every declared digest and fail if any dependency changes. The release is built in a unique isolated SwiftPM scratch directory from that same snapshot. The signed bundle signature authenticates the final executable and embedded manifest together; it is verified at runtime against the pinned signer. Any behavior/input change therefore changes a signed source/build digest and cannot run under an old promotion even if a developer forgets to bump a version label. This is a trusted-packager attestation, not a reproducible-build proof.
- **Registry uniqueness:** The production registry validates that every accepted candidate ID/version pair maps to at most one profile. Duplicate identities are a registry integrity error and cannot be resolved by first-match order.

Original strategy, Mac, and research design challenges: PASS. Expanded configuration/code-identity challenge: PASS. Do not put an executable digest in a manifest that is embedded before signing: this creates a signing cycle. Instead, generate the build-input manifest before signing and embed it as a resource. It records exact source/dependency-closure hashes, `Package.swift`, `Package.resolved` when present, Swift toolchain, build flags/configuration, generated/macro-produced inputs and their generators, and build-manifest schema. Then sign the complete app bundle with the pinned owner identity. At runtime, verify the fixed bundle ID, the complete non-ad-hoc code signature and pinned signer, and the signed resource manifest. The operating system's code-signature verification binds the executable and embedded manifest to the same signed bundle; the manifest must not claim to contain a self-referential executable hash. The trusted staged packager is responsible for generating the manifest from the exact source snapshot, hashing before/after the isolated build, and failing on drift. Add packaging/runtime tests that mutate the executable and manifest independently after signing and prove signature verification rejects both. This scheme relies on the owner-pinned signing key and reviewed packager as the build attestation trust root; no source-to-binary reproducibility claim is made. The independent challenge confirms the cycle and trust assumptions are adequately resolved. Runtime package acceptance still requires an owner-pinned signing identity.

## Promotion manifest independent review — 2026-11-14

The independent reviewer verified that the three earlier implementation defects are corrected: the signer trust anchor is the compile-time `OwnerSignerPin.certificateSHA1` (empty by default), evaluator/adapter/selector hashes match exact registered source paths, and campaign plus approval evidence repeat the profile source-closure digest. The reviewer also confirmed the recorded focused 6/6, full 588/588, and release Mac target build evidence. The review is **PARTIAL**, because `sourceClosureSHA256` covers only `Sources/` paths. `Package.swift`, optional `Package.resolved`, packager, Swift toolchain/SDK and build flags are recorded globally in the build manifest but are not part of the digest repeated by the promotion binding, campaign, and owner approval. Existing campaign/approval evidence can therefore remain valid after those build inputs change.

### Debate outcome: manifest build-input binding

- **Failure case:** change a behavior-affecting global build input (including package graph, toolchain/SDK, build flags, or trusted packager), regenerate/rewrite the package binding to the new source-only closure, and retain old campaign and approval records. Runtime can compare the unchanged source-only closure and accept those records even though the reviewed build environment changed.
- **Counterargument considered:** the code signature authenticates the manifest and executable together, and the manifest records global build inputs. That proves the current bundle's manifest was signed, but it does not bind historical campaign/approval artifacts to those recorded global inputs; the old artifacts only repeat the narrower source digest.
- **Required correction:** bind one canonical, domain-separated per-profile promotion-input digest that includes the profile source closure and the declared global build context (package/lockfile state and digests, packager and manifest generator inputs, toolchain/SDK identity, build flags/configuration, and declared generated inputs). The package binding, campaign evidence, and separate owner approval must all carry that same digest; runtime must recompute/validate it against the signed build-input manifest before exposing any promotion. Schema versions must make old source-only evidence fail closed.
- **Minimum acceptance cases:** change each class of global build input independently and prove the per-profile digest changes; prove stale campaign and approval evidence fail after merely rewriting the package binding; prove malformed, omitted, duplicate, or unsupported-schema digest material rejects promotions; prove empty production package still passes and the owner signer pin remains fail-closed.

### Remediation plan and checklist

Goal: close the evidence binding gap only. Do not expand strategy coverage, set a signer pin, enable any production promotion, or alter order authority.

**Resolved plan:** use a schema-v2 per-profile `promotionInputDigest` combining (a) the exact sorted profile source closure and (b) one complete global build-input envelope shared across profiles. The global envelope uses explicit typed input roles and includes package/lockfile state and digests, trusted packager and manifest-generator inputs, declared macro/plugin/generator and generated-input provenance, toolchain/compiler plus SDK identity, bundle/target/configuration/architecture/deployment settings, and the effective ordered build flags. Missing required classes, duplicate normalized paths, unknown roles, unsafe paths, malformed digests, unsupported schemas, or canonicalization failures reject promotions. Bind the resulting digest in the promotion package binding, campaign evidence and separate owner approval; runtime recomputes it from the signed v2 manifest and compares all copies before returning any record. Do not auto-upgrade v1 source-only evidence. Any global build input change intentionally invalidates every profile's campaign/approval; profile-only source edits invalidate that profile. Keep the pre-sign executable out of the manifest to avoid a signing cycle; the OS code signature continues to seal executable and manifest together, without a reproducible-build claim. Production promotions remain empty.

**Independent design challenge: PASS.** The read-only challenge confirmed the original gap and supports this two-layer contract. It specifically advised classifying required global inputs rather than inferring them as every path outside a profile closure; pinning array ordering semantics (sorted for sets, original order for build argv); representing optional `Package.resolved` absence explicitly; rejecting v1 evidence; adding canonical golden vectors; and testing each global-input mutation, campaign/approval tampering, and staged pre/post drift. The principal tradeoff is conservative global invalidation: toolchain/package/packager changes invalidate all profiles, which is safer and simpler than maintaining separate partial global dependencies.

## Follow-up debate — trusted package build environment — 2026-11-14

Independent review of the v2 implementation found that the staged script invokes `swift run` and `swift build` while inheriting the caller's environment. The manifest records a fixed argv template, `swift --version`, `xcode-select -p`, SDK version/path and a hardcoded deployment target, but does not reject or bind environment overrides such as `DEVELOPER_DIR`, `TOOLCHAINS`, `SDKROOT`, `MACOSX_DEPLOYMENT_TARGET`, compiler overrides, Swift/compiler/linker flags or a custom `PATH`. A different effective build environment could therefore produce the same promotion digest. This is an independent review finding; v2 remains unintegrated until resolved.

**Debate outcome:** a second read-only challenge agrees that hashing the entire caller environment is brittle and can expose secrets while still failing to prove which compiler ran. It recommends a minimal `env -i` build environment shared by every SwiftPM invocation, a reviewed allowlist, isolated `HOME`/`TMPDIR`, fixed `PATH` and locale, explicit selected `DEVELOPER_DIR` and deployment target, and rejection/inventory of repo-local `.swiftpm` configuration. It also recommends binding resolved tool paths and build identities, SDK settings digest, Xcode build and target triple, and verifying the selected Apple-signed installation. Hashing the entire Xcode/SDK tree is rejected as impractical and not a reproducible-build claim; the signed Apple toolchain installation is an explicit trust root.

### Resolved plan: controlled macOS build environment

Goal: make the v2 manifest describe the effective package build, regardless of caller environment, and ensure all generator/build/verify commands use the same controlled toolchain context.

1. The staged packager resolves the active developer directory using `/usr/bin/xcode-select` under a clean environment. It runs every `swift run`, `swift build`, and `--show-bin-path` command via `/usr/bin/env -i` and absolute `/usr/bin/swift`, with a reviewed deterministic allowlist: resolved `DEVELOPER_DIR`, fixed system `PATH`, per-build isolated `HOME` and `TMPDIR`, stable locale, and explicit `MACOSX_DEPLOYMENT_TARGET=14.0`. Signing identity is never passed into SwiftPM environment.
2. `env -i` drops caller overrides including `TOOLCHAINS`, `SDKROOT`, `SWIFT_EXEC`/`SWIFTC`, `SWIFT_DRIVER_*`, Swift/compiler/linker flags, `CC`/`CXX`/`LD`, `ARCHS`, `ONLY_ACTIVE_ARCH`, and `DYLD_*`; fixed `PATH` prevents tool shadowing. Manifest generation and pre/post verification see the exact same allowlist. Isolated scratch paths are identified by policy (`isolated`), not their random absolute values.
3. Generator rejects a repository-local `.swiftpm` directory unless its full configuration is explicitly included; for this slice, fail closed. It captures resolved `swift`, `swiftc`, `swift-frontend`, and `clang` paths and version/build identities, selected Xcode version/build and code-signature identity, resolved SDK path/version plus `SDKSettings.plist` digest, target triple/architecture, deployment target, and effective ordered argv. It verifies those captured values against the controlled environment at generation and verification.
4. The selected system Xcode/toolchain code signature is verified and its signer identity is included in the global v2 envelope. Do not hash the entire Xcode or SDK tree and do not claim reproducible source-to-binary attestation; rely on the reviewed packager, pinned app signer, Apple-signed selected toolchain, and OS bundle signature as trust roots. If no valid selected toolchain identity is available, manifest generation fails closed.
5. Add a subprocess probe test/script that poisons caller override variables and PATH, runs a child through the exact controlled wrapper, and verifies the child observes only allowlisted values. Add tests for `.swiftpm` fail-closed behavior and generation/build/verify identity drift. Keep production promotions empty and owner app signer pin empty.

**Independent design challenge: PASS.** The read-only challenger confirmed that controlled environment plus captured effective values is preferable to hashing arbitrary environment. It specifically called for isolating HOME to prevent user SwiftPM mirrors, explicitly handling repo-local `.swiftpm`, verifying actual resolved compiler/SDK selection rather than trusting version labels, preserving legitimate signing only for the later codesign stage, and poisoning override variables in tests. It accepted the tradeoff that unsupported custom toolchains fail closed.
