## Debate

Two independent read-only audits agree that the native `ORBBreakRetestV1` evaluator is the strategy currently running in active Trade. `LightningDeskModel.evaluateORB` builds completed M1 bars and returns a pure `ORBDecision`; the live refresh and FX scan both call `publishORBDecision`. The publisher persists a candidate `V3TradePlan`, but no production active-Trade path writes `V3SetupLifecycleEvent`. `BreakoutAcceptanceLifecycleV1` is an independent research hypothesis and must not be wired as a surrogate evaluator.

The V3 lifecycle store already validates append-only streams, but its current progression rules do not cover ORB's natural stages. ORB may report `forming → watching`, `watching → confirmed` while a retest is still pending, then `approaching` while a retest confirmation forms. A lifecycle writer cannot copy `decision.setupState` directly. The contract's `quoteSequence` is quote-specific; ORB consumes candles and has no quote sequence, so timestamps or candle IDs must not be placed in that field.

The live publisher awaits plan persistence and uses generation checks before and after I/O. A lifecycle append introduces the same stale-generation and actor-reentrancy questions. It must not mutate plan publication or suggest an entry/fill if lifecycle storage fails.

## Ranked scope proposal

1. Add a pure ORB lifecycle projection that maps completed ORB evaluation evidence to observation-only V3 setup states. Start only after the opening range is sealed; ignore pre-session/no-data/incomplete-range results. Proposed monotonic mapping: sealed range and transient boundary approach → `watching`; breakout/retest pending and retest confirmation pending → `approaching`; validated ORB candidate → `confirmed`; structural invalidation → `invalidated`; setup timeout → `setupExpired`. No `triggered` or position state is emitted.
2. Give each stream a stable setup ID derived from instrument, provider/environment, ORB session start, strategy/configuration digest, and engine version. Give transition IDs a stable digest of setup ID, projected state, and canonical source input digest. Do not include polling/record time in identity. Same state without a lifecycle transition produces no event.
3. Carry explicit config/input digests, engine version, stable structure identity, timeframe, evidence schema, source bar IDs and source time. For lifecycle `sourceTime`, use the last relevant completed bar's interval close/availability time (`ORBBar.endTime`), never interval start; a bar is eligible only if `endTime <= evaluation asOf`. Keep `quoteSequence` nil for ORB. Order bar-sourced events by unique, strictly increasing close times; equal source times fail closed.
4. Extend V3 lifecycle validation only for evidence-complete `ORB_BREAK_RETEST_V1` events and the precisely allowed monotonic ORB transitions. Preserve existing default and Breakout Acceptance behavior. Replayed terminal setups on the same ORB session remain terminal; a new session/configuration gets a distinct setup identity.
5. In the authenticated Live OANDA branch of `publishORBDecision`, reload/reconcile this setup's persisted tail and append only a genuine transition. Attach `planID` only to the event that observes the validated plan; earlier lifecycle events may have nil plan IDs. Keep lifecycle write/read failure in a separate evidence-status channel and do not alter the ORB decision, candidate plan projection, or manual-only safeguards.
6. Add tests for state projection/transitions, initial observations without invented history, source observation ID matching cited bar evidence, stable identity, live-only gating, exact replay/conflict, out-of-order/corrupt stream/write failures, concurrent refresh/scan, stale generation, terminal re-arm prevention, plan-ID attachment, Review visibility, and proof that no entry/position/outcome records are produced.

## Design contract proposed for challenge

- Writer runs only for authenticated `OANDA_LIVE` observations in `Research/live-oanda`; Practice, proxy, simulated, non-FX, missing-session, or stale-generation input cannot write.
- Lifecycle is an observation record. `confirmed` means the strategy's observed setup passed its confirmation rules. It is not a broker order, execution, fill, or position.
- Setup identity is stable across repeated scans of one frozen opening range and changes with session, instrument, strategy/configuration, engine, provider, or environment.
- Event IDs exclude wall-clock polling time. Exact replay after a fresh store load is a no-op; an existing event ID with changed substantive evidence is a conflict. Only `receivedAt` and `recordedAt` may vary on a retry, and the first stored timestamps are retained.
- ORB state projection is monotonic: `WATCHING → APPROACHING → CONFIRMED`, or `WATCHING/APPROACHING → INVALIDATED/SETUP_EXPIRED`. Transient boundary proximity does not advance or regress persisted lifecycle state. No `quoteSequence` value is fabricated.
- Earlier events may have nil `planID`. The `CONFIRMED` event links only the exact candidate plan ID.
- Persist before reporting the event as durable. Status distinguishes `notAttempted`, `notApplicable`, `noTransition` (stream read/validation succeeds with no new transition needed), `recorded` (a new event was appended), `structureSuppressed` (this opening range already reached an ORB-confirmed, invalidated, or expired state and cannot re-arm after a config revision), and `unavailable`. Structure suppression is a one-setup-per-range rule and does not imply broker execution, plan failure, or current setup invalidity. A labeled, accessible Trade research-status value exposes it. A lifecycle write failure exposes evidence-unavailable status but leaves current strategy/plan projection unchanged. Check generation immediately before append; a superseded generation cannot publish stale status. A successfully written historical event remains valid evidence for its source observation.
- A corrupt archive, invalid transition, identity conflict, stale/out-of-order source bars, or failed write does not advance a stream cursor or report success. Exact same-state rescans append no new event.
- No new entries, positions, fills, outcomes, broker synchronization, order actions, or manual position-entry path.

## Questions raised for independent design challenge

The first and second challenge rounds raised source-time/order semantics, process-wide serialization across store actors, retry timestamp equivalence, append-boundary generation checking, and visible status meanings. These were amended and re-challenged. Final independent design review: **PASS**. It also required that the first event use the actually observed projected state without invented predecessors, and that its source observation ID match cited bar evidence; both are acceptance requirements above.

## Independent design challenge — amendment pass

First challenge: **PARTIAL**. The independent reviewer accepted the safety boundary and monotonic projection but found the contracts incomplete for source ordering, replay, actor concurrency, stale generations, and visible failure status. Second challenge: **PARTIAL**. It confirmed the bar-close source-time choice but asked for an explicit cross-instance coordinator, exact retry equivalence, recorded/no-transition distinction, and a generation check immediately before append. The design is amended as follows:

- ORB streams use a distinct source-time order: all events must have non-nil, unique, strictly increasing completed-bar close/availability `sourceTime` from `ORBBar.endTime`; bars are eligible only when `endTime <= evaluation asOf`. `quoteSequence` stays nil and may not be mixed into an ORB stream. Equal source times are ambiguous and fail closed. Existing quote-sequenced streams retain their current ordering and rules.
- ORB complete provenance is strategy-scoped and requires valid configuration/input digests, engine, stable nonempty unique source bar IDs, structure/session identity, timeframe, and schema version, with no fabricated quote sequence. ORB transition validation is checked before the generic state graph and allows only explicitly listed ORB progressions; all other strategies retain current transition behavior. Add negative cases for missing/mismatched provenance and fabricated sequence values.
- `ResearchStore` uses a named shared per-standardized-root `ResearchStoreLifecycleLockRegistry` to serialize lifecycle tail read, replay/predecessor validation, idempotency check, and append across separate store actor instances in the app process. An existing event ID is a duplicate only when all substantive fields match (including predecessor/state, plan ID, reason, source identity/time/bar IDs, digests, environment, strategy, and engine); only `receivedAt` and `recordedAt` may differ, and original stored timestamps are retained. Same ID with any changed substantive field is a hard conflict. Event identity excludes poll time; concurrent calls through two stores for the same root have deterministic one-write/one-duplicate outcomes. Cross-process writers are outside this app-process slice.
- A durable append from a superseded generation remains historical evidence. Its completion cannot update the newer generation's visible state. The next current generation reconciles from the durable tail before appending. Tests cover old-generation success and failure after a newer generation begins.
- Lifecycle persistence status is separate from ORB decision/plan state and distinguishes `notAttempted`, `notApplicable`, `noTransition` (stream read/validation succeeds with no state change needed), `recorded` (a new event was appended), `structureSuppressed` (the same frozen opening range already reached a confirmed, invalidated, or expired ORB state), and `unavailable`. This one-setup-per-range suppression does not imply broker execution or a failed/invalid current plan. A labeled, accessible Trade research-status value exposes it. Persistence failure never implies invalid setup or failed plan; current plan publication and manual-only rules remain independent.
- For a confirmed candidate, persist the plan before writing the lifecycle transition that references its plan ID. If plan persistence fails, do not append a confirmed lifecycle event pointing at an absent plan. Lifecycle-only failures do not withdraw an already persisted plan or alter the ORB decision.
- Check generation immediately before beginning append. A write already started may remain valid historical evidence after supersession, but its completion never changes newer visible state. The next current generation reconciles from the durable tail; tests control old-generation success and failure.

Final transition map remains: start after the opening range is sealed; transient boundary movement is `WATCHING`; breakout/retest pending is `APPROACHING`; candidate accepted by ORB rules is `CONFIRMED`; terminal structural failure is `INVALIDATED`; time limit is `SETUP_EXPIRED`. No intermediate or out-of-order state is fabricated.
